# 任务记录一致性修复 Job 技术方案

## 目标

在既有任务执行记录之上增加一个有界、幂等、可停止的后台修复 Job，收敛“Session 已进入终态，但任务或执行尝试仍停留在未完成状态”的记录。修复不改变 Session、消息、通知或执行调度，不新增任务尝试、数据库迁移或公开接口。

## 触发与范围

- 生命周期启动时注册 `TaskRecordRepairService`，随后每 60 秒扫描一轮；首轮在启动后立即执行。
- 单轮最多处理 100 个候选任务，避免历史积压一次性占满数据库连接。
- 只处理 Session 已处于 `COMPLETED` / `FAILED` / `CANCELLED` 的记录，且会话最后活动时间已超过 120 秒宽限期，避开正常的 `finishExecution` / `settleExecution` 收口窗口。
- 只修复已经存在的 Task / Execution 行。完全缺失的任务记录没有可靠的执行 ID 与开始时间，不能凭空重建；原始外部事件去重仍不在本方案范围。

## 修复规则

候选条件：Session 为终态、超过宽限期，并且满足任一条件：

1. 存在 `WORKING` / `BLOCKED` 执行尝试。
2. Task 的 `stage` 或 `lastExecutionId` 与最新执行尝试不一致。
3. 没有任何执行尝试，但 Task 仍为非终态或保留了不存在的 `lastExecutionId`。

每个候选在独立数据库事务中重新锁定 Session 并复核终态，然后执行：

- 最新执行尝试仍未完成时，收敛为 Session 的终态；`COMPLETED` / `CANCELLED` 清空失败原因。
- 更早的未完成尝试统一标记为 `FAILED`，写入修复时间与固定原因 `执行已结束但任务记录未收口，已自动修复`。
- Task 的 `stage`、`lastExecutionId` 收敛到最新执行尝试；没有执行尝试时，`stage` 收敛到 Session 终态并清空无效执行 ID。
- 不修改已经结算的最新尝试，不覆盖非空终态结果，不创建新的 Task / Execution / Trigger。

结束时间使用实际修复时间，不尝试还原原始终态时刻。重复扫描同一记录不会产生额外写入。

## 并发与故障边界

- Session 行锁让修复与同一会话的正常开始/结算串行；终态和最新尝试会在锁内重新读取，不依赖扫描时的快照。
- 多实例同时运行时可能重复扫描同一候选，但行锁、终态条件和幂等写入使重复修复安全；本方案仍不提供数据库租约。
- 扫描、单个任务修复或存储异常只记录日志，不抛出到应用生命周期，不影响正在执行的会话。
- Job 在停机处理器中先停止定时器，不新增执行队列；已在途的单轮修复仍按既有数据库连接关闭顺序自然结束或记录失败。

## 验证

- 最新 `WORKING` / `BLOCKED` 尝试按 Session 终态收敛，旧尝试失败关闭。
- 活跃 Session、已收敛终态、最新终态尝试不被改写。
- Task 无执行记录、`lastExecutionId` 指向旧尝试或不存在执行时能够收敛。
- 重复扫描幂等，扫描异常不抛出。
- 候选 SQL 只选择终态会话、宽限期外且存在未完成或不一致记录的任务。

## 非目标

- 不回填历史 Session，不重建完全缺失的任务记录。
- 不恢复 `WAITING_APPROVAL` / `CANCELLING`，不改变崩溃恢复范围。
- 不新增跨渠道归并、上游事件去重、Watchdog、LLM Router 或数据库执行租约。
