# Webhook 触发器失效会话绑定恢复设计

## 背景

`webhook_trigger.session_id` 可绑定固定会话；为 `NULL` 时每次触发新建会话。此前会话删除只回收定时任务、MCP 快照、工作区规则、通道映射和消息队列，没有处理 Webhook 触发器。

删除被绑定的会话后，触发器仍保持启用并携带旧 `session_id`。下一次外部 Webhook 会通过验签与调用流水登记，但 `OpenRunService` 在会话锁内重读会话时抛出 `SESSION_NOT_FOUND`。该错误既不属于预算拒绝，也不属于准入拒绝，因此不计入连败、不会自动停用；外部系统每次请求都会失败，只能人工修改触发器。

## 目标

- 删除会话时立即把仍指向该会话的 Webhook 触发器解绑为 `NULL`。
- 对历史残留、并发竞态或清理失败，首次触发撞到 `SESSION_NOT_FOUND` 时自动解绑并重试一次。
- 重试成功后本次请求正常执行；重试仍失败时才写拒绝流水并返回错误。
- 条件解绑只清理仍指向本次失效会话的绑定，不覆盖用户并发改绑的新会话。
- 清理失败不阻断会话删除，也不影响后续请求自愈。

## 非目标

- 不删除触发器、不重置密钥、不改变启停状态或连续失败计数。
- 不改变 `session_id = NULL` 的既有语义：每次触发新建会话。
- 不自动把绑定改到其他已有会话；没有“新建会话”之外的回退目标。
- 不改变验签、限流、准入、幂等和调用流水的正常语义。

## 实现

### 会话删除即时解绑

`create-app.ts` 在 `onSessionDeleted` 回调末尾通过延迟解引用调用
`WebhookTriggerService.clearSessionBindingBySessionId(sessionId)`，执行：

```sql
UPDATE webhook_trigger SET session_id = NULL WHERE session_id = ?
```

`webhook_trigger` 增加 `session_id` 索引（V194），避免每次会话删除扫描整表。该步骤单独捕获异常并告警，不影响会话删除结果。

### 触发时自愈

`WebhookTriggerService.handleFire()` 首次调用 `openRun.run()` 抛出 `SESSION_NOT_FOUND` 且触发器仍绑定旧会话时：

1. 执行条件解绑：

```sql
UPDATE webhook_trigger SET session_id = NULL WHERE id = ? AND session_id = ?
```

2. 条件更新命中，或重新读取发现绑定已被删除钩子清空时，以 `sessionId = NULL` 重试一次。
3. 重试成功则正常写 accepted 流水与终态计数；首次失败不提前写 rejected。
4. 条件更新未命中且触发器已被改绑到其他会话时，不回退重试，原样返回首次错误，避免把旧事件投到新会话。
5. 重试仍失败时，只按重试错误写一次拒绝流水；预算 / 准入拒绝继续沿用原连败计数规则。

## 边界

- 触发器已删除：条件更新影响 0 行且重新读取为空，不重试。
- 删除钩子与触发自愈并发：两者都只把指向旧会话的绑定置空，重复执行幂等。
- 用户并发改绑到其他会话：旧请求不重试，不会误用新绑定。
- 调用流水在首次 `begin` 时可能记录旧 `session_id`；重试成功后由 `markAccepted` 回写新会话，幂等回放使用最终新会话。
- 历史残留无需数据回填；下一次删除或触发会收敛，数据库层只新增索引。

## 测试

- 绑定会话已删除后首次触发自动解绑、按新会话重试成功，后续触发不再携带旧会话。
- 解绑后重试仍失败时只执行两次，拒绝流水只写一次。
- 并发改绑其他会话时不重试、不误投。
- 会话删除路径调用批量解绑。
- 仓储 SQL 覆盖无条件批量解绑与条件解绑，并校验受影响行数。
