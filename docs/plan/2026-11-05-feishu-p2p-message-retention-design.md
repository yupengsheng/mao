# 飞书私聊消息映射保留清理设计

## 背景

`feishu_p2p_message` 为每条飞书私聊入站与出站消息记录「消息 → 会话」归属，用于两类读取：

- 用户引用某条历史消息时，定位该消息所属会话并切换活跃会话。
- 发送回复前查询当前会话最近一条入站消息，作为 reply 目标。

映射行只增不减：每条私聊消息（含机器人文本回复、进度卡片、排队卡片）都会插入一行。长期运行后表会随消息量线性增长，并持续占用存储与索引。

## 目标

- 每小时清理一次超过 180 天的私聊消息映射。
- 单批最多删除 5000 条，单轮最多 20 批，避免长事务和大范围锁。
- 清理幂等，多实例重复执行安全；异常只记录日志，不阻断进程。
- 新增 `(created_at, id)` 索引，支撑 `WHERE created_at < ? ORDER BY created_at, id LIMIT n`。

## 非目标

- 不清理 180 天内的映射，也不按用户、机器人或会话单独配置保留期。
- 不删除 `feishu_session_channel`（会话 → 通道绑定）与 `feishu_thread_session`（话题 → 会话映射）；它们按会话/话题而非消息增长，删除会破坏长期会话路由。
- 不修改 `feishu_group_message_log` 的 30 天保留策略。
- 不归档被删除的映射，删除后不能从数据库恢复。

## 保留期决策

- **180 天**：与审计日志、LLM 调用流水、会话活动等长期治理数据的默认保留期一致，覆盖绝大多数「翻历史消息后引用切换」场景。
- 用户引用超过 180 天的消息时，映射查询返回 `null`，入站处理器按既有降级逻辑静默保持当前会话；消息仍会正常进入当前会话执行。
- 发送回复所需的最近入站映射由新消息实时写入，不受历史清理影响。
- **每小时执行**：与现有入站事件、群消息日志等清理 Job 一致；单轮未完成时跳过后续触发。

## 索引

现有唯一键 `(app_id, message_id)` 与 `(app_id, session_id)` 都无法服务跨会话按时间清理。V186 增加：

- `feishu_p2p_message (created_at, id)`

使用 `ALGORITHM=INPLACE, LOCK=NONE` 在线加索引，避免阻塞映射写入。

## 实现

- `FeishuP2pMessageCleanup` 使用 `setInterval` 每小时触发，`stopped` 控制生命周期，`cleaning` 防止同一进程内重复扫描。
- `MysqlFeishuMessageRepository.deleteP2pMessageBatch(cutoff, limit)` 执行 `DELETE ... WHERE created_at < ? ORDER BY created_at, id LIMIT n`，并将 `limit` 钳制到 `1..5000`。
- cutoff 通过 `formatDateTime` 生成，与数据库时间字段格式一致。
- 调度器装配到 `assembleLifecycle`，关闭流程显式调用 `stop()`。

## 并发与边界

- 多实例同时运行时可能并发删除同一批行，条件相同且删除幂等，不引入跨实例租约。
- 单轮达到 20 批上限时剩余记录留到下一小时继续清理。
- 清理与写入并发时，新写入行的 `created_at` 一定晚于 cutoff，不会被误删。
- 删除仅影响引用切换的会话定位与历史 reply 目标查询，不影响消息内容、会话历史或当前会话执行。
- 引用超期消息不会再自动切换到原会话；需要回到历史会话时，可在该会话内发送新消息或使用既有会话切换方式。
